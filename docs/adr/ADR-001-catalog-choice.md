# ADR-001 — Metadata catalog: OpenMetadata over DataHub

| | |
|---|---|
| **Status** | Accepted |
| **Date** | 2026-08-26 |
| **Decider** | Benoît Chevrier |
| **Project** | `data_governance_demo` |
| **Supersedes** | — |

---

## 1. Context

This project publicly demonstrates the foundations of an **operational Data Office** on a public real-estate dataset.

**The objective function behind this trade-off is not that of an enterprise decision.** Three constraints dominate here:

1. **Reproducibility by an unassisted third party.**
2. **Governance legibility.** The thesis is about operationalised governance, not lineage alone. Maximum visibility in the UI is the goal.
3. **A three-week delivery window**, handled by a single person, with no room to absorb the learning cost of a distributed architecture.

---

## 2. Options considered

| # | Option | Nature |
|---|---|---|
| A | **OpenMetadata** | Catalog + governance + quality, single server |
| B | **DataHub** | Catalog + governance, distributed event-driven architecture |
| C | **Marquez / OpenLineage alone** | Lineage only |
| D | **Amundsen** | Discovery, minimal governance |
| E | **Apache Atlas** | Legacy governance, coupled to the Hadoop ecosystem |
| F | **dbt docs alone** | Documentation and lineage generated by the dbt project |

## 3. Criteria and weighting

| Criterion | Weight | Rationale for the weight |
|---|---:|---|
| Clone-and-run reproducibility (RAM, container count, versionable compose file) | **25 %** | Hard requirement. First point of failure with the reader. |
| Governance legibility on screen / DMBOK coverage | **25 %** | This is the thesis itself. Lineage without a glossary or ownership does not prove a Data Office. |
| Learning cost relative to the delivery window | **20 %** | Three weeks, a single contributor. |
| Defensibility under technical probing | **15 %** | Every technical choice in the repository must be justifiable. |
| Market name recognition | **10 %** | Taken into account, but not decisive given the constraints at hand. |
| Generative-AI agenda signal | **5 %** | Differentiation bonus, not structural. |

## 4. Evaluation

Scores out of 5, weighted per the grid above.

| Criterion | Weight | **OpenMetadata** | **DataHub** |
|---|---:|:---:|:---:|
| Reproducibility | 25 % | **4** | **2** |
| Governance / DMBOK | 25 % | **5** | **4** |
| Learning cost | 20 % | **4** | **2** |
| Defensibility | 15 % | **4** | **4** |
| Market recognition | 10 % | **4** | **5** |
| AI signal | 5 % | **5** | **4** |
| **Weighted total** | | **4.30** | **3.20** |

### Rationale for the decisive gaps

**Reproducibility — 4 against 2.** DataHub documents *2 CPUs, 8 GB of RAM, 2 GB of swap and 13 GB of disk* for 14 containers, and its supported installation path is the `datahub docker quickstart` CLI wrapper, which downloads a generated compose file into `~/.datahub/`. Two unfavourable consequences: an 8 GB Docker allocation effectively rules out 8 GB laptops and strains 16 GB ones; more importantly, the compose file is not *written* by the author but generated by the vendor — the repository would no longer show its engineering, only the ability to run a supplied script. OpenMetadata asks for *6 GiB and 4 vCPUs* and publishes an official compose file meant to be versioned, hence readable, annotatable and defensible. That file declares 5 services (PostgreSQL, Elasticsearch, a one-shot migration container, the server, and the ingestion worker) — counted directly in the 1.13.4 release asset on 2026-08-27.

**Governance / DMBOK — 5 against 4.** OpenMetadata natively bundles, in a single server, the objects that materialise the DMBOK knowledge areas: a business glossary with an approval workflow, classification and tagging (including PII), ownership and stewardship, quality tests and data contracts, and — since 2.0 — structured intake forms for certification and ownership assignment, plus OWL taxonomy import. DataHub covers glossary, domains and assertions, but delegates most of the quality layer to third-party integrations (Great Expectations, dbt): the demonstration would require one more component, hence more RAM and more time, for a result that is less unified on screen.

**Learning cost — 4 against 2.** DataHub requires understanding Kafka, the *GMS* and the *Actions Framework* before producing anything defensible. OpenMetadata embeds Airflow for ingestion: orchestration is demonstrated without an additional component, which **settles the Airflow / Dagster trade-off by side effect**.

**Market recognition — 4 against 5.** DataHub has greater seniority and a larger audience (≈ 12.6k GitHub stars, originating at LinkedIn). At a 10 % weight, this does not reverse the decision given the constraints at hand.

---

## 5. Decision

**Adopt OpenMetadata**, **pinned to `1.13.4`** — the latest stable release of the 1.x branch, verified against the registry on 2026-08-27. This ADR originally assumed branch `1.12.x` and required the exact tag to be confirmed at the first `docker compose up`: that check fired, and `1.13.4` (released 2026-08-21) supersedes it. The reasoning is unchanged, only the version number.

Version 2.0 is excluded because it shipped on **24 August 2026, two days before this decision**.

Pinning the stable N-1 under a firm delivery date, then documenting the migration path, is an operating-model decision.

---

## 6. Rejected alternatives

| Option | Reason for rejection |
|---|---|
| **DataHub** | An 8 GB, 14-container footprint against the reproducibility constraint; a CLI-wrapper installation path that moves the engineering outside the repository; a learning cost (Kafka, GMS, Actions) incompatible with the window. Remains the better choice for a high-volume enterprise context, or one already invested in event-driven tooling. |
| **Marquez / OpenLineage alone** | Excellent lineage, but no governance objects: no glossary, no classification, no ownership, no quality. It would prove lineage, not a Data Office — the inverse of the thesis. |
| **Amundsen** | Discovery-oriented; weak governance coverage; markedly slowed community momentum. A dated technology-watch signal. |
| **Apache Atlas** | Historic coupling to the Hadoop ecosystem, dated ergonomics. |
| **dbt docs alone** | Provides good lineage for free, but no governance objects. **Not rejected as a component**: retained as the *source* of the lineage fed into OpenMetadata, which is the cheapest ingestion path in the project. Rejected only as the catalog. |

---

## 7. Consequences

### Favourable
- A `docker-compose.yml` written, commented and versioned in the repository: the engineering is visible.
- Orchestration is demonstrated through the embedded Airflow, with no extra component — **Dagster leaves the scope**.
- Glossary, classification, ownership and quality live in a single UI: the five-minute walkthrough works without switching tabs.
- Column-level lineage comes from the official dbt connector rather than being hand-authored.

### Accepted downsides
- 6 GiB of RAM remains a high bar: the `README` must state it in its first section, along with a documented fallback.
- Lower name recognition than DataHub: to be offset by the quality of this ADR, which becomes an argument in itself.
- Deliberate version debt on the 1.x branch, to be settled in v1.1.

### Explicitly incurred debt
| Debt | Target |
|---|---|
| Migration to OpenMetadata 2.0 + enabling the MCP server | v1.1 |
| Superset dashboards | v1.2, or dropped if it adds no demonstrative value |
| mkdocs documentation on GitHub Pages | v1.1 |

---

## 8. Review triggers

This ADR should be revisited if any of the following occurs:
- a priority target organisation already runs DataHub (the trade-off then flips on the recognition criterion);
- OpenMetadata 2.1 stabilises the Kubernetes orchestrator and leaves 1.x unsupported;
- the memory footprint proves blocking during Sprint 0 (trigger: startup failure under a 6 GiB Docker allocation).
